# 输出目的地与订阅

自 v2.12.0 起，`--output` 统一传送运行日志和采集事件。省略该参数时默认写入 `stdout`。显式设置目的地会**替换**默认值。如果要同时写往两个位置，应分别指定两次。

```bash
sudo ecapture tls --model text --text-source pcapng \
  --output stdout --output capture.jsonl
```

## 不同目的地收到什么

| 目的地 | 文本模式 | 原生 keylog 模式 | 原生 pcapng 模式 |
| --- | --- | --- | --- |
| `--output stdout` 或 `stderr` | 带标签的日志和解码文本 | 日志和带标签的 NSS 密钥行 | 日志和带标签的字节数摘要 |
| `--output PATH` 或 `file:///PATH` | Protobuf v2 JSON Lines，含日志和 `TEXT` 事件 | JSON Lines，仅运行日志 | JSON Lines，仅运行日志 |
| `--output tcp://HOST:PORT` | 主动连接，发送含日志与 `TEXT` 事件的 JSON Lines | 日志和 `KEYLOG` 字节 | 日志和 `PCAPNG` 字节 |
| `--stream-listen ws://HOST:PORT/PATH` | 客户端连入后收到二进制 v2 日志及事件 | 二进制 v2，含 `KEYLOG` 字节 | 二进制 v2，含 `PCAPNG` 字节 |

终端每行都带有 `log_type=log` 或 `log_type=event` 以及模块名，事件还会标明格式。在 JSON Lines 中，读取每条 v2 `LogEntry` 的 `log_type` 字段即可区分记录。运行日志和采集事件的实际枚举值分别是 `LOG_TYPE_PROCESS_LOG` 和 `LOG_TYPE_EVENT`。原生文件与 `--output` 文件的路径必须不同。[输出 API](https://github.com/gojue/ecapture/blob/v2.12.0/docs/event-forward-api.md)

如果使用 v2.12.0 之后的开发版，终端输出和上表中的正式版有两处差异。原生 pcapng 模式仅打印运行日志。多行 TEXT 事件只在开头打印一次前缀，SDK 文本首行还增加了 `pid` 和 `pname`。[pcapng 终端变更](https://github.com/gojue/ecapture/commit/669a5f742d1f2cbe2d21a29f203764ceb90e27fa) · [TEXT 输出变更](https://github.com/gojue/ecapture/commit/71e191ceb90bcfa2497a88e25c16f10044d4bbdc) · [eCaptureQ 解析兼容性](/q/zh/protocols/#raw)

## 订阅采集器

```bash
sudo ecapture tls --model text --text-source pcapng \
  --stream-listen ws://127.0.0.1:28256/
```

接收端须连接配置的路径，发送有效的 HTTP `Origin` 头，并协商 WebSocket 子协议 `ecapture.v2`。上游 Go 客户端示例使用 `Origin: http://localhost/`。每条二进制消息含一条 Protobuf v2 `LogEntry`。订阅后第一条消息是心跳，随后是当前可用的 `collector_info` 快照、最多 128 条近期运行日志及实时事件。快照记录当前模块、模式和数据源，以及可用的主机、构建和目的地信息。此监听默认关闭，启用后提供明文 WS，无内建身份认证。在同机的 eCaptureQ 中可填写 `ws://127.0.0.1:28256/` 作为数据源。[eCaptureQ 快速开始](/q/zh/quick-start/) · [线协议](https://github.com/gojue/ecapture/blob/v2.12.0/protobuf/PROTOCOLS.md) · [接收端示例](https://github.com/gojue/ecapture/blob/v2.12.0/examples/ecaptureq_client/README.md)

对于 TCP 输出，采集器会主动连接已监听的接收端。接收端应累积收到的字节，直到换行符标记一条完整的 JSON 记录。对原生 `LOG_TYPE_EVENT`，先读取 `event_payload.capture_format`，再按顺序写出 `event_payload.keylog.data` 或 `event_payload.pcapng.data` 解码后的字节。ProtoJSON 解码器已将 base64 字段转换为字节。单个 NSS 密钥行或 pcapng 块可能横跨多条记录。

热重载进入新一轮采集时会关闭现有连接。TCP 会重新连接，WebSocket 客户端则需重新订阅。接收端应为每个连接新建文件。较晚加入的 pcapng 客户端只获得文件头和之后的数据包与密钥。仅凭 TCP EOF 无法确认完整结束，中断的文件应保留为部分结果。采集器本地的原生文件则在重载时继续追加。[连接和完成条件](https://github.com/gojue/ecapture/blob/v2.12.0/docs/event-forward-api.md)

## 迁移 v2.8–v2.11 命令

| 旧参数或用法 | v2.12.0 的迁移方式 |
| --- | --- |
| `--eventaddr`、`--logaddr`、`-l` | 多次指定 `--output` 以选择终端、文件或 TCP。文件和 TCP 接收端改为解析 v2 JSON Lines。 |
| 主动推送到 `ws://`、`wss://`，或使用 `--ecaptureq` | 改用 v2 WebSocket 客户端连接 `--stream-listen`，或使用 JSON Lines 接收端接收主动 TCP 输出。 |
| `--listen` | 用 `--config-listen HOST:PORT` 启用独立的 HTTP 配置服务。 |
| `--eventroratesize`、`--eventroratetime` | 移除两个参数。v2.12.0 没有文件轮转命令行选项。 |
| 使用默认文件名或重定向 stdout 保存原生文件 | 对应模式须显式指定本地 `--keylogfile` 或 `--pcapfile`。 |

这些旧参数已经移除，没有兼容别名。输出目的地和监听地址在启动时确定，修改它们需要重启采集器。[v2.12.0 迁移说明](https://github.com/gojue/ecapture/blob/v2.12.0/CHANGELOG.md)
