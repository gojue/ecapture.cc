# 模式选择：Text、Keylog 或 pcapng

## 按所需产物选择

| 模式 | 工作负载提供的输入 | 本地产物 | v2 网络接收端取得的数据 |
| --- | --- | --- | --- |
| `--model text --text-source pcapng`（默认） | 一张网卡上的数据包及 TLS 密钥 | 可选 `--pcapfile` 和/或 `--keylogfile` | 解码后的 `TEXT` 及可用元数据 |
| `--model text --text-source hook` | TLS 库或 Go 函数的读写数据 | 通过 `--output` 写入格式化事件 | 单次调用产生的 `TEXT` |
| `--model keylog` | TLS 密钥 | 必填 `--keylogfile`，使用 NSS Key Log 格式 | 含 NSS 编码字节的 `KEYLOG` |
| `--model pcapng` | 一张网卡上的数据包及 TLS 密钥 | 必填 `--pcapfile`，可选 `--keylogfile` | 含 pcapng 编码字节的 `PCAPNG` |

各模式都会产生运行日志。文本模式的本地 `--output` 文件按 Protobuf v2 JSON Lines 格式记录日志和事件，原生模式的本地 `--output` 文件仅记录日志。原生文件与 JSON Lines 文件须使用不同路径。[目的地与模式对照表](https://github.com/gojue/ecapture/blob/v2.12.0/docs/event-forward-api.md)

## 同一个 OpenSSL 请求的三种示例

```bash
sudo ecapture tls --model text --text-source pcapng --output stdout --output session.jsonl
sudo ecapture tls --model keylog --keylogfile session.keys
sudo ecapture tls --model pcapng --pcapfile session.pcapng
```

选择一条命令启动，再建立测试连接。对于 Go 工作负载，换成 `gotls --elfpath /path/to/app`。Linux GnuTLS 程序选用 `gnutls`，库不在自动搜索路径中时使用 `--gnutls` 指定。实际流量在另一张网卡上时，使用 `-i` 指定网卡。

## 选择验证方法

- 查看解码消息时，检查同一连接上的请求路径和响应。一次套接字读取可能只包含部分消息，也可能读到多条消息，这会影响显式 hook 数据源的输出。
- 验证密钥日志时，同时独立抓取同一连接的数据包。仅凭密钥无法查看包的顺序、重传或请求内容。
- 验证 pcapng 时，在 Wireshark 中打开原生文件。文件中可能包含缺少匹配密钥的网络包，应在解密后的流中查找已知的应用消息。

如果既要马上查看请求，又要保留网络包供复核，在第一条命令中增加 `--pcapfile session.pcapng`。此时网络事件类型仍为 `TEXT`。[使用 Wireshark 验证解密结果](3.6-wireshark-decryption-workflows.md)
