# Wireshark 解密工作流

选择一个可以通过路径或响应标记识别的测试请求。先启动采集器及独立抓包工具，再建立连接。验证的目标是在解密后的数据流中找到这条应用消息。

## 使用内嵌密钥的抓包

```bash
sudo ecapture tls --model pcapng --pcapfile session.pcapng -i lo 'tcp port 8443'
```

此例假设自己的 OpenSSL HTTPS 服务监听回环地址的 8443 端口。新建请求，再停止 eCapture。用 Wireshark 打开 `session.pcapng`，选中测试连接并追踪 TLS 流。数据包块中是加密流量，DSB 中是解密密钥。如果使用 `--model text --text-source pcapng --pcapfile session.pcapng`，生成的文件与实时解码器收到的 pcapng 数据流相同。

DSB 可能晚于其对应的数据包到达。使用 Wireshark 4.4 或更新版的工具独立验证时，可以从同一份抓包中提取内嵌密钥，写入私有临时文件，读取抓包时预加载这些密钥。以下命令读取编号为 0 的 TLS 流。

```bash
keys=$(mktemp)
editcap --extract-secrets session.pcapng - > "$keys"
tshark -n -r session.pcapng -o "tls.keylog_file:$keys" -q -z follow,tls,ascii,0
rm -f -- "$keys"
```

如果文件中有多个 TLS 连接，应选择目标流，并以已知的测试内容验证结果。仅统计包数无法判断是否成功解密。[内嵌密钥验证方法](https://github.com/gojue/ecapture/blob/v2.12.0/README.md#live-decryption-for-text-output)

## 将独立抓包与密钥日志配对

1. 在承载测试连接的接口启动抓包，例如 `sudo tcpdump -i lo -w network.pcap 'tcp port 8443'`。
2. 在另一个终端运行 `sudo ecapture tls --model keylog --keylogfile session.keys`。等两个工具就绪后发起请求，再分别停止采集。
3. 用 Wireshark 打开 `network.pcap`，在 **Preferences → Protocols → TLS** 中将 (Pre)-Master-Secret log filename 设为 `session.keys`。追踪测试连接并核对其中已知的请求或响应。

使用 TShark 也可以在离线抓包中读取编号为 0 的 TLS 流。

```bash
tshark -n -r network.pcap -o tls.keylog_file:session.keys -q -z follow,tls,ascii,0
```

如果密钥来自其他连接，或抓包错过握手，数据流可能仍然显示为密文。调整协议设置前，先核实网卡、测试时间和会话是否匹配。[独立密钥日志示例](https://github.com/gojue/ecapture/blob/v2.12.0/docs/example-outputs.md)

## 查看进程归属

可选的 Wireshark 插件 `utils/ecapture.lua` 能显示 eCapture 记录到的 PID、进程名和采集时的程序参数。参数快照最多 256 字节，超出时显示截断标记。未取得归属的包不会被赋予进程身份。插件添加的进程字段与 Wireshark 的 TLS 解密彼此独立。如果只想迅速确认一次 HTTP 请求，可直接查看[文本模式](3.2-text-mode.md)的实时输出。[Wireshark 插件](https://github.com/gojue/ecapture/blob/v2.12.0/utils/ecapture.lua)
