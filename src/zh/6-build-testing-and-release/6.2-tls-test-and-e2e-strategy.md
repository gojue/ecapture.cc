# TLS 测试与端到端 (E2E) 策略

## 每类测试验证什么

单元测试用过短、带填充、最大长度的样本验证解码器，并检查模块配置和版本映射。在 Linux 上，`go test -v -race ./...` 检查默认标签构建。验证生产路径时，先用 `make all` 生成实际字节码，再运行 `make test-race`。使用生产标签执行 lint 也需要对应目标构建出的 libpcap。[构建与测试说明](https://github.com/gojue/ecapture/blob/v2.12.0/docs/agent/build-test.md)

维护中的 Linux E2E 在 Ubuntu 22.04+ 或 Debian 13+ 上运行，要求 root 和支持 eBPF 的内核。测试使用可复现的本地客户端，并通过独立的 Wireshark 解码器比对结果。pcapng/QUIC 检查需要 `tshark` 和 `editcap` 4.4+，C 客户端还需 OpenSSL、GnuTLS 开发头文件。

```sh
make all
sudo make e2e-linux
# 只运行 GoTLS 的两种原生文件模式。
sudo env E2E_MODULES=gotls E2E_MODES='keylog pcapng' bash test/e2e/run_e2e.sh
```

| 被测模式 | 判断依据 |
| --- | --- |
| 默认文本 | 捕获尚在运行时即可观察到预期请求或响应。用例检查 TLS 1.2 和 1.3，并用可选 pcapng 内嵌的密钥独立解密。针对旧路径的用例显式传入 `--text-source hook`。 |
| Keylog | 本地 NSS 文件中的 TLS 1.2、1.3 密钥都能解开另行抓取的数据包。 |
| Pcapng | 本地文件包含段头、接口描述、包和 TLS 解密密钥块。只使用文件内嵌密钥即可解密。 |
| 输出与重载 | Linux 三个核心模块均验证带标签的 stdout、JSON Lines 文件与 TCP、二进制 v2 订阅、同模块 HTTP 重载。原生模式的 `--output` 文件只能出现运行日志。 |

## 协议与平台覆盖

GoTLS 用例包括跨 TCP 分段的 HTTP/1.1、HTTP/2 正文，QUIC v1/v2 上的 HTTP/3，二进制 TLS，以及 DNS over TLS/HTTPS/QUIC、增量 SSE/gRPC。HTTP/3 基线使用两个并发连接，每个连接有两个请求流，并独立解密各流正文。该基线未覆盖迁移、0-RTT 或全部 QUIC 状态。OpenSSL 用例检查 TLS 1.3 双向 KeyUpdate、DTLS 1.2 ECDHE-RSA AES-GCM 和 `SSL_clear` 后的连接复用。GnuTLS 的 keylog 用例要求两个 TLS 版本均能解密。

Android E2E 需要 Linux 主机以及有 root 权限的 API 33+ 设备或模拟器。客户端使用系统 Conscrypt/BoringSSL，在探针就绪后才发出 HTTPS 请求。CI 覆盖 API 33–36。原生 LoongArch 端到端任务在专用 Debian 主机上运行 OpenSSL、GoTLS 的 CO-RE 用例。非核心 Shell 和数据库模块的测试有独立入口，保留的旧输出检查不计入 v2 传输验证。[E2E 覆盖矩阵与入口](https://github.com/gojue/ecapture/blob/v2.12.0/test/e2e/README.md) · [Linux 工作流](https://github.com/gojue/ecapture/blob/v2.12.0/.github/workflows/e2e.yml) · [Android 工作流](https://github.com/gojue/ecapture/blob/v2.12.0/.github/workflows/android_e2e.yml)
