# Protobuf 与外部集成

## 目的与范围

本文档描述 ecapture 基于 protobuf 的事件序列化格式和外部集成能力。从版本 0.8.0 开始，ecapture 通过 Protocol Buffers 提供结构化事件流，支持与外部工具、图形界面和分析平台的实时集成。有关基于文本的控制台输出信息，请参阅 [4.1 文本输出模式](4.1-text-output-mode.md)。有关 PCAP 文件生成，请参阅 [4.2 PCAP 集成](4.2-pcap-integration.md)。

protobuf 格式支持：
- 结构化事件序列化，便于程序化处理
- WebSocket 流式传输，用于实时事件交付
- 与 eCaptureQ 图形界面集成
- HTTP API 用于远程配置和事件转发
- 与 Burp Suite 等工具的兼容性，用于安全分析

### 事件类型枚举

`Event` 消息中的 `type` 字段对应于 [pkg/event_processor/iparser.go:25-47](https://github.com/gojue/ecapture/blob/ca085d05/pkg/event_processor/iparser.go#L25-L47) 中定义的 `ParserType` 枚举，指示应如何解释载荷：

| ParserType 值 | 常量名称 | 描述 |
|--------------|---------|------|
| 0 | `ParserTypeNull` | 原始二进制数据，未应用解析（DefaultParser） |
| 1 | `ParserTypeHttpRequest` | HTTP/1.x 请求 |
| 2 | `ParserTypeHttp2Request` | HTTP/2 请求，带 HPACK 解压缩 |
| 3 | `ParserTypeHttpResponse` | HTTP/1.x 响应 |
| 4 | `ParserTypeHttp2Response` | HTTP/2 响应，带 HPACK 解压缩 |
| 5 | `ParserTypeWebSocket` | WebSocket 帧 |

解析器类型在 `NewParser()` 函数 [pkg/event_processor/iparser.go:85-115](https://github.com/gojue/ecapture/blob/ca085d05/pkg/event_processor/iparser.go#L85-L115) 中通过内容检测动态确定。对载荷调用每个注册解析器的 `detect()` 方法，第一个成功匹配的解析器决定解析器类型。如果没有解析器匹配，则使用 `DefaultParser` 并设置 `ParserTypeNull`。

## 流水线中的事件序列化

### EventProcessor 到 Protobuf 的转换

当事件流经事件处理流水线时，它们在输出阶段被转换为 protobuf 格式。转换发生在 `eventWorker.Display()` 方法中：

```mermaid
sequenceDiagram
    participant IEventStruct as "IEventStruct<br/>(输入事件)"
    participant Worker as "eventWorker"
    participant Parser as "IParser<br/>(HTTP/HTTP2/Default)"
    participant LogEntry as "pb.LogEntry"
    participant Output as "outComing chan"
    
    IEventStruct->>Worker: Write(event)
    Worker->>Worker: writeEvent(event)
    Note over Worker: 在 bytes.Buffer 中<br/>累积载荷
    
    Worker->>Worker: 触发 Display()
    Worker->>Parser: Write(accumulated_bytes)
    Parser->>Parser: 解析载荷<br/>(HTTP/HTTP2/等)
    Parser-->>Worker: Display() 返回<br/>解析后的字节
    
    alt 不是 CollectorWriter
        Worker->>IEventStruct: ToProtobufEvent()
        IEventStruct-->>Worker: pb.Event
        Worker->>LogEntry: 创建 LogEntry<br/>设置 LOG_TYPE_EVENT
        Worker->>LogEntry: 设置 EventPayload
        LogEntry->>LogEntry: proto.Marshal()
        LogEntry-->>Worker: []byte (序列化后)
    else 是 CollectorWriter (文本模式)
        Worker->>Worker: 格式化为文本
        Note over Worker: PID, Comm, IPs, payload
    end
    
    Worker->>Output: writeToChan(bytes)
```

**事件到 Protobuf 的转换序列**

关键区别在于配置的 logger 是否实现了 `CollectorWriter` 接口。如果没有，事件将被序列化为 protobuf；否则，它们被格式化为人类可读的文本。

来源：[pkg/event_processor/iworker.go:174-228](https://github.com/gojue/ecapture/blob/ca085d05/pkg/event_processor/iworker.go#L174-L228), [user/event/ievent.go:54-70](https://github.com/gojue/ecapture/blob/ca085d05/user/event/ievent.go#L54-L70)

### WebSocket 协议

客户端连接到端口 28257 的 WebSocket 端点，并接收 protobuf 序列化的 `LogEntry` 消息的连续流。每个 WebSocket 消息包含恰好一个作为二进制数据封送的 `pb.LogEntry`：

| 字段 | 类型 | 描述 |
|------|------|------|
| WebSocket 消息 | 二进制 | 包含一个通过 `proto.Marshal()` 封送的 `pb.LogEntry` |
| `LogEntry.log_type` | 枚举 | `LOG_TYPE_EVENT`, `LOG_TYPE_HEARTBEAT`, 或 `LOG_TYPE_PROCESS_LOG` |
| `LogEntry.event_payload` | `pb.Event` | 当 `log_type == LOG_TYPE_EVENT` 时存在 |
| `LogEntry.heartbeat_payload` | `pb.Heartbeat` | 当 `log_type == LOG_TYPE_HEARTBEAT` 时存在 |
| `LogEntry.run_log` | string | 当 `log_type == LOG_TYPE_PROCESS_LOG` 时存在 |

**客户端集成步骤：**

1. 建立到 `ws://localhost:28257/` 的 WebSocket 连接（或 `wss://` 用于 TLS）
2. 持续读取二进制 WebSocket 消息
3. 使用 `proto.Unmarshal()` 将每条消息解组为 `pb.LogEntry`
4. 根据 `log_type` 切换以确定哪个载荷字段包含数据
5. 对于 `LOG_TYPE_EVENT`，访问 `event_payload` 以获取捕获的数据

protobuf 封送发生在 [pkg/event_processor/iworker.go:222-226](https://github.com/gojue/ecapture/blob/ca085d05/pkg/event_processor/iworker.go#L222-L226)，其中 `proto.Marshal(le)` 在发送到 `outComing` 通道之前序列化 `LogEntry`。

来源：[pkg/event_processor/iworker.go:214-227](https://github.com/gojue/ecapture/blob/ca085d05/pkg/event_processor/iworker.go#L214-L227), [protobuf/PROTOCOLS.md:54-62](https://github.com/gojue/ecapture/blob/ca085d05/protobuf/PROTOCOLS.md#L54-L62), [protobuf/PROTOCOLS.md:68-96](https://github.com/gojue/ecapture/blob/ca085d05/protobuf/PROTOCOLS.md#L68-L96)

### 集成模式与远程模式

eCaptureQ 支持两种部署模型：

| 模式 | 描述 | 客户端平台 | 服务器平台 |
|------|------|-----------|-----------|
| **集成** | eCaptureQ 捆绑 ecapture 二进制并在本地运行 | Linux, Android | 不适用（仅本地） |
| **远程** | eCaptureQ 连接到远程 ecapture 服务器 | Windows, macOS, Linux | Linux, Android |

在集成模式下，eCaptureQ 生成 ecapture 进程并通过 localhost 连接到其 WebSocket 端点。在远程模式下，用户配置远程服务器地址，eCaptureQ 通过网络建立 WebSocket 连接。

### WebSocket 客户端示例

对于自定义集成，客户端可以直接连接到 ecapture 在端口 28257 上的 WebSocket 端点。`utils/protobuf_visualizer/pb_debugger.go` 中存在一个参考客户端实现，演示了集成模式：

**示例客户端流程（伪代码）**

```
import websocket
import protobuf_gen.ecaptureq_pb2 as pb

# 连接到事件流
ws = websocket.connect("ws://127.0.0.1:28257/")

while True:
    # 接收二进制消息
    message = ws.recv()
    
    # 解组 protobuf
    log_entry = pb.LogEntry()
    log_entry.ParseFromString(message)
    
    # 根据类型处理
    if log_entry.log_type == pb.LOG_TYPE_EVENT:
        event = log_entry.event_payload
        print(f"UUID: {event.uuid}")
        print(f"协议类型: {event.type}")
        print(f"PID: {event.pid} ({event.pname})")
        print(f"载荷长度: {event.length}")
        print(f"数据: {event.payload[:100]}...")
    elif log_entry.log_type == pb.LOG_TYPE_HEARTBEAT:
        hb = log_entry.heartbeat_payload
        print(f"心跳: count={hb.count}, msg={hb.message}")
```

[utils/protobuf_visualizer/pb_debugger.go](https://github.com/gojue/ecapture/blob/ca085d05/utils/protobuf_visualizer/pb_debugger.go) 中的 Go 参考实现展示了紧凑模式、十六进制显示和载荷截断的命令行选项。protobuf 模式定义记录在 [protobuf/PROTOCOLS.md](https://github.com/gojue/ecapture/blob/ca085d05/protobuf/PROTOCOLS.md) 中。

## 集成安全考虑

### 网络绑定与访问控制

WebSocket 和 HTTP 服务器默认绑定到 `localhost`，将访问限制在本地机器：

```mermaid
graph TB
    subgraph "默认配置"
        Localhost["监听: localhost:28256<br/>监听: localhost:28257"]
        LocalOnly["仅可从<br/>同一机器访问"]
        
        Localhost --> LocalOnly
    end
    
    subgraph "远程访问模式"
        SSHTunnel["SSH 隧道<br/>ssh -L 28257:localhost:28257"]
        VPN["VPN 连接<br/>私有网络"]
        DirectExpose["直接暴露<br/>(不推荐)"]
        
        SSHTunnel -->|"安全"| RemoteClient["远程客户端"]
        VPN -->|"安全"| RemoteClient
        DirectExpose -->|"不安全"| RemoteClient
    end
```

**远程访问的安全最佳实践**

1. **仅本地绑定**：默认的 `localhost` 绑定防止网络暴露 [README_JA.md:83](https://github.com/gojue/ecapture/blob/ca085d05/README_JA.md#L83)
2. **SSH 隧道**：对于远程访问，使用 SSH 端口转发：
   ```bash
   ssh -L 28257:localhost:28257 user@remote-server
   ```
3. **root 权限要求**：ecapture 需要 root/CAP_BPF，提供操作系统级别的访问控制
4. **无内置身份验证**：截至当前版本，WebSocket 接口不实现身份验证
5. **网络隔离**：当需要远程访问时，在隔离或受信任的网络上部署 ecapture

### 数据隐私考虑

protobuf 事件流包含来自捕获的 SSL/TLS 连接的明文载荷数据：

| 数据类型 | 敏感度 | 考虑事项 |
|---------|--------|---------|
| TLS 载荷 | **高** | 包含解密的 HTTPS 数据、凭证、API 密钥 |
| 连接元数据 | **中** | 源/目标 IP、端口、PID 暴露网络拓扑 |
| 进程名称 | **低** | 进程名称（pname 字段）可能揭示运行的应用程序 |

**安全建议：**

- 将 WebSocket 流视为与原始数据包捕获在敏感度方面等同
- 如果通过网络传输，为 WebSocket 连接实现 TLS（wss://）
- 确保符合组织数据处理策略
- 考虑在静态存储中加密存储的 protobuf 日志
- 在长期存储中轮换或编辑敏感数据
